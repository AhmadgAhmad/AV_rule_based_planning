Teaching the Planner to Read the Road

Right now ContextDetector looks at two numbers, speed limit and junction distance, and picks one of four labels with an if/elif chain. Today you're replacing that with a small network that reads a short window of driving history and outputs a probability over all four contexts at once. This page walks through why, and exactly how.

01 · The Problem

Rules don't generalize, and they don't blend

The current detector is a single frame of state run through hard thresholds: 

if junction_or_light_ahead:
    ctx = Context.INTERSECTION
elif speed_limit > 50:
    ctx = Context.HIGHWAY
elif speed_limit < 20:
    ctx = Context.PARKING
else:
    ctx = Context.CITY

Two things break here. First, it only ever looks at this instant, so a car briefly slowing for a pothole on the highway can get relabeled CITY for one tick and back. Second, the label is hard: 19m from a junction is INTERSECTION, 21m is CITY, and eta_p2's weights jump discontinuously across that line even though nothing about the driving situation actually changed that much.

What you want instead: something that looks at a short window of recent driving state, and outputs a confidence over all four contexts rather than a single hard pick. That's a sequence classifier.

02 · Framing

Yes, it's classification. Three questions to answer.

Every supervised ML problem comes down to three things: what goes in, what architecture turns it into what comes out, and what number you minimize to make that mapping good. Here's ours.

Input

The last 15 ticks (0.75s) of a 14-dimensional feature vector: speed, acceleration, yaw rate, lane info, junction and light distance, nearby traffic. Shape (15, 14).

Architecture

A GRU reads the window and produces a hidden state summarizing recent history, then a small MLP head maps that hidden state to 4 class scores.

Output

A softmax over 4 classes: INTERSECTION, HIGHWAY, CITY, PARKING. Not a hard label. A distribution you can threshold, blend, or feed straight into P2's weights.

The only thing that makes this different from a textbook classification problem is the "window of history" part. A single tick of state is noisy and ambiguous right at context boundaries; a short sequence lets the network smooth over that noise the same way you'd naturally judge "are we near an intersection" by watching the last second of driving, not by freezing one frame.

04 · Architecture

GRU in, softmax out

A GRU (Gated Recurrent Unit) is a small recurrent network built to summarize a sequence into one vector, deciding at each step how much of the new input to blend in versus how much of what it already knew to keep. That's exactly what you want here: "was the last second mostly highway-like, with maybe a brief wobble that shouldn't flip the label."

15 ticks of feature vectors → GRU → final hidden state → MLP head → softmax over 4 contexts
class ContextGRU(nn.Module):
    def __init__(self, feature_dim=14, hidden_size=48, num_classes=4):
        self.gru = nn.GRU(feature_dim, hidden_size, batch_first=True)
        self.head = nn.Sequential(
            nn.Linear(hidden_size, hidden_size // 2), nn.ReLU(),
            nn.Linear(hidden_size // 2, num_classes),
        )

    def forward(self, x):          # x: (batch, 15, 14)
        out, _ = self.gru(x)          # (batch, 15, 48)
        last_hidden = out[:, -1, :]   # final tick's summary
        return self.head(last_hidden)  # (batch, 4) logits

This is a genuinely small network, on the order of ten thousand parameters. "Deep" here means "has temporal structure," not "many layers." A Transformer would be overkill at this sequence length and would just invite the question of why you didn't use a GRU.

05 · Cost Function

Cross-entropy, plus one optional term

The main loss is ordinary categorical cross-entropy: it compares the predicted probability the network assigned to the correct class against 1.0, and penalizes it more the further off it is. Nothing exotic. Two additions are worth having in your back pocket: 

def context_loss(logits, targets, class_weights=None,
                 prev_logits=None, temporal_weight=0.1):
    ce = F.cross_entropy(logits, targets, weight=class_weights)
    loss = ce
    if prev_logits is not None:
        # penalize the prediction jumping a lot between
        # consecutive ticks when nothing dramatic happened
        p, p_prev = F.softmax(logits, -1), F.softmax(prev_logits, -1)
        loss += temporal_weight * F.mse_loss(p, p_prev.detach())
    return loss
  • class_weights: your drives will naturally have far more CITY and HIGHWAY frames than PARKING ones, unless you specifically go park the car. Up-weighting rare classes stops the network from just predicting the majority class every time.
  • temporal_weight: this is the fix for the exact "jumps discontinuously at the boundary" problem from Section 01. It's off by default in train_context_model.py, turn it on once the basic classifier is working.
06 · Data Generation

Where labels come from (and the honest caveat)

CARLA doesn't hand you a "context" label. context_data_logger.py derives one from privileged map and traffic state, richer than the current detector's two inputs, but still a rule, not a human annotation.

Worth saying out loud

If you generated training labels using the current rule-based detector, you'd just be training a network to imitate the heuristic you're trying to replace, an expensive way to reproduce the same reductive logic. The labeler in derive_label() uses extra signal the current detector never sees (the map's own lane-type tag, traffic light proximity) specifically so the network has more to learn from than the rule it's replacing.

Concretely, today's plan with the scenario suite:

  1. Attach ContextDataLogger to the tick loop of scenarios 1–4 (and ideally a few plain autopilot drives through Town04 and Town05 for broader coverage).
  2. Each tick, it writes one CSV row: the 14 features plus a weak-supervision label.
  3. One CSV file per drive = one route. Keep routes separate, don't merge them into one giant file.
Stronger labels later

If the per-tick rule ever feels too noisy once you look at real data, the cleanest upgrade isn't a fancier rule, it's bucketing by known map geography instead (e.g. Town04's highway loop road IDs). That trades generality for near-perfect labels on the towns you've mapped, worth it for a clean result section. See the note at the bottom of context_data_logger.py.

07 · Splitting the Data

Split by route, never by row

Every tick in a drive looks almost identical to the tick right before it. If you shuffle all rows together and split randomly, near-duplicate frames from the same drive end up on both sides of the split, and your validation accuracy will look great for the wrong reason.

This is exactly what split_routes() in train_context_model.py does: it shuffles and splits the list of CSV files, then builds windows only within each file. A window never straddles two different drives either, since that would mix unrelated history together.

Check Your Understanding

Four questions before you start training

Why 15 ticks and not just 1?+
A single tick is a snapshot, and snapshots right at a context boundary are ambiguous by definition, is 19m from a junction "intersection" or not. A window lets the GRU weigh recent trend, was the car consistently slowing and turning, rather than reacting to one noisy instant. 15 ticks at 20 Hz is 0.75s of history, roughly matching the REPLAN_INTERVAL scale the planner already replans on.
Why output a softmax instead of just the most likely class?+
A hard label throws away exactly the information you need to fix the "eta_p2 jumps discontinuously" problem. A soft distribution lets you blend the P2 weight vectors proportionally to how confident the network is in each context, so a 60/30/5/5 split between INTERSECTION and CITY produces a smoothly interpolated weighting instead of a step function.
Why is training on the current rule-based labels not a real improvement?+
If your labels come from the exact same if/elif chain you're replacing, the best the network can ever do is memorize that chain, it has no path to being more accurate than its teacher. That's why derive_label() pulls in extra signal (lane type tags, light proximity) the current detector never uses at all, so there's genuinely more to learn.
Why split by whole route instead of shuffling all rows together?+
Adjacent ticks in one drive are nearly identical to each other. If a random split puts tick 401 in train and tick 402 in validation, the model isn't being tested on anything new, it's basically seen that exact frame already. Splitting by whole CSV file (whole drives) means validation routes are genuinely unseen.
